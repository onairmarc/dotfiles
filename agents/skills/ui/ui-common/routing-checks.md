# Routing checks

Use these as dry-run scenarios after changing descriptions or routes. They test the intended process, not a claim about automatic harness invocation.
For each case, select the owner, identify optional help, and check the mode and stopping point without editing an application.

## Scenarios

- **“Build a new landing page for a botanical archive.”** Load `ui-common` and local owner `frontend-design`. Derive a subject-specific
  direction. Load interaction/mobile/motion guidance only where the actual design needs it; don't force scroll reveals or a dependency install.
- **“Tidy this existing admin table.”** Preserve its tokens and density. Use visual and resilience guidance for alignment, long identifiers, and comparison.
  Don't turn a dense task into a grid of oversized cards or invent a new identity.
- **“The save dialog loses my changes on failure.”** Use interaction guidance, trace submission and error recovery, repair in scope, and prove input survives.
  A new palette or toast library doesn't solve the state bug.
- **“Make this command menu feel alive.”** Use motion guidance, inspect frequency and purpose, and keep repeated keyboard work immediate. Reject ornamental
  delays while preserving useful feedback. Don't invoke explicit-only `review-animations` or `pick-ui-library` on your own.
- **“This drawer stutters while navigation loads.”** Use motion guidance and available `animation-performance`; trace the driver and record the bottleneck.
  Don't promise GPU execution from a transform string or add broad `will-change` without evidence.
- **“Bottom actions disappear behind the iPhone keyboard.”** Use mobile guidance and available `mobile-native`. Trace shell and scroll ownership, check
  software-keyboard behavior, preserve zoom, and distinguish code/emulation checks from physical-device proof.
- **“Test this card with horrible data; don't edit it.”** Use resilience guidance in review-only mode. Inspect contracts and report reproduction cases;
  don't add a picker, tighten validation, or edit the card without permission.
- **“Fix overflow for long translated names.”** Use resilience guidance in repair mode. Reproduce through fixtures, fix the layout, and verify ordinary data.
  Don't force the user to approve a known mechanical fix again or shorten accepted names to protect the layout.
- **“Show three ways this pricing selector could work.”** Use exploration guidance. Build distinct, dev-only working alternatives; compare fairly, recommend,
  and wait for selection. Don't promote a favorite or create a worktree.
- **“Review this screen and suggest improvements.”** Use review guidance and relevant lenses. Separate confirmed defects from a few task-based opportunities.
  No edits, automatic plans, or invented findings to fill a quota.
- **“Add press feedback to our Expo screen.”** Use motion and interaction guidance plus available `animate-expo`. Verify the installed SDK/library APIs.
  Don't apply DOM events, CSS viewport fixes, or web-only recipes to native controls.
- **“The toast renders twice.”** Use interaction guidance and available `ask-sonner`; trace mounts and emitters in the installed version before changing code.
  Don't assume every duplicate comes from a second toaster or that layering is solved by a larger z-index.

## Absence and conflict checks

- With every optional third-party skill missing, each scenario still has a local owner and usable rules. Don't install skills just to complete routing.
- With a referenced skill absent from the public repo, check repo and user-level locations before declaring it missing. Preserve explicit-only boundaries.
- With different contents under a familiar skill name, trust the loaded `SKILL.md` over this inventory's summary; keep governing scope and safety rules.
- With a product-documented longer sheet transition, inspect purpose, continuity, and measured behavior rather than flagging the duration alone.
- With reduced motion enabled, accept a static change or short fade. Don't add scale to satisfy a source rule that conflicts with that preference.
- With browser tooling or hardware unavailable, identify exactly which checks remain unverified. Don't describe source inspection as a visual test.

Pass when each request reaches its narrow owner, optional skills remain optional, and mutation and completion stay within the request.
